Requerimiento 1 Consistencia y lectura / escritura

Dos caras de la misma base: AP para leer, CP para vender

Lectura de catálogo y usuarios AP · eventual

Redis cache-aside (TTL 60 s / 30 s) → secundario Mongo secondaryPreferred. Si Redis cae, se sigue leyendo (fail-soft).

Escritura de pedidos y pagos CP · fuerte

Siempre en el primario: writeConcern y readConcern majority (2 de 3 nodos confirman) + transacciones multi-documento.

💡 El GET de un producto puede mostrar stock con segundos de atraso — es aceptable porque la decisión de venta nunca usa ese dato: la toma la reserva atómica en el primario.

~1 min. Mostrar "Cache miss" y "Escritura". Frase clave: la lectura puede estar atrasada, la venta no.

Requerimiento 1 "Un pedido debe ser único"

Pedido único: Idempotency-Key con doble barrera

  1. Redis SET idem:{key} ord_… NX EX 24h — barrera rápida
  2. MongoDB índice único en idempotency_key — barrera definitiva si Redis no está
  3. La reserva usa _id = pedido_id: un pedido no puede reservar dos veces
—
~30 s. Primer intento crea; reintento con la misma clave devuelve el mismo pedido (200 + Idempotent-Replay) sin cobrar ni reservar de nuevo.
Requerimiento 2 Modelado de datos NoSQL

MongoDB + Redis · embebido vs. referencia

MongoDB 8 — documental

Los agregados son documentos JSON (como el anexo). Atomicidad por documento (stock), transacciones, replica set y write/read concerns por operación: CP y AP con la misma tecnología.

Redis 7 — clave-valor en memoria

Lectura sub-ms para el lado AP, TTL que acota la consistencia eventual y SET NX atómico para la idempotencia.

    ¿Por qué orquestación?

    Flujo secuencial con un dueño claro, la lógica de compensación en un solo lugar y el estado de cada transacción consultable en GET /api/pedidos/{id}.

    • Log persistido con w:majority
    • Job reintenta las fallidas → converge

    Requerimiento 3 Patrón Chain of Responsibility · Servicio de Pedidos y Pagos

    Chain of Responsibility: cada manejador hace una sola cosa

    Falla en:

    Clase base ManejadorPedido

    public final void manejar(ContextoPedido ctx) {
  String detalle = procesar(ctx);   // lanza si falla
  ctx.pedido().registrarPaso(paso(), OK, detalle);
  ctx.persistir();
  if (siguiente != null) siguiente.manejar(ctx);
}

    Armado en un solo lugar (CadenaConfig): agregar o reordenar validaciones no toca a los demás.

    Orquestador de la SAGA

    La cadena define qué y en qué orden. Si un eslabón lanza RechazoPedidoException, el orquestador corta la cadena y desapila las compensaciones.

    Más allá de la letra · Resiliencia

    ¿Y si un servicio se cae en medio de la SAGA?

    A · Catálogo detenido

    Falla la conexión → la petición nunca llegó → no hay nada que compensar → ABORTADA

    B · Catálogo congelado

    Conecta pero no responde → resultado desconocido → la compensación se intenta y se reintenta hasta converger.

    Probado con docker compose pause catalogo-service · scripts/prueba-fallas-red.sh
    1 · Reservar

    POST reserva → el catálogo está congelado

    2 · Timeout

    5 s sin respuesta. ¿Reservó o no? No se sabe

    3 · Compensar

    DELETE reserva también falla → COMPENSACION_FALLIDA

    4 · Vuelve

    El catálogo procesa la reserva atrasada: stock 5 → 3 😱

    5 · Job (30 s)

    ReintentadorCompensaciones: DELETE reserva → stock 3 → 5

    6 · Converge

    Saga COMPENSADA, reserva LIBERADA. Consistencia eventual garantizada

    ~30 s. El punto clave: distinguimos "no llegó" de "no sé si llegó", y como todas las compensaciones son idempotentes, reintentarlas es seguro.
